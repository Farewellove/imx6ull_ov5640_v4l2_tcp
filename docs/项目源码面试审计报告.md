# 1. 项目概述

## 1.1 项目要解决的问题

在 NXP i.MX6ULL 嵌入式平台上, 通过 V4L2 框架驱动 OV5640 摄像头 (mx6s_capture 驱动, 驱动名 mx6s-csi, 8-bit 并行 DVP 接口), 将采集到的图像帧通过 TCP 网络传输到 PC 端, 实现实时查看和保存。同时支持板载 LCD 本地显示 (framebuffer) 和 PC 端 SDL2 窗口显示。

## 1.3 输入/输出/实现效果

**输入**:
- OV5640 摄像头实时视频流 (8-bit 并行 DVP, D[7:0] + PCLK + HSYNC + VSYNC)
- 命令行参数: 设备节点 (-d)、服务器 IP (-s)、端口 (-p)、分辨率 (-w/-h)、格式 (-f)、帧数 (-n)、LCD 开关 (-l)

**输出**:
- TCP 网络流 (自定义帧协议 FRAME_MAGIC + frame_header + raw data)
- 板载 LCD: YUYV→XRGB8888 (BT.601 定点) / RGB565→XRGB8888 (解包+位扩展) 转换后写入 32bpp 显存
- PC 端: raw 文件 (.rgb565/.yuv/.mjpg) + PPM 文件 (.ppm) + SDL2 实时显示窗口

**实现效果**: 采集→TCP发送→PC端接收保存并实时显示, 全链路打通。

## 1.5 完整工作流程 (一段话)

> 在 i.MX6ULL 板端, 用户态程序 `imx6ull_sender` 通过 V4L2 MMAP 接口从 `/dev/video1` (mx6s-csi/mx6s_capture 驱动, OV5640 传感器, 8-bit 并行 DVP) 采集图像帧。采集流程严格遵循 V4L2 规范: open→QUERYCAP→S_FMT→REQBUFS(count=3)→mmap→QBUF→STREAMON→poll+DQBUF 循环。每一帧采集后, 构造 40 字节的 frame_header (含魔数、宽高、像素格式、时间戳等, 全部网络字节序), 通过 TCP 发送到 PC 端。同时可选将帧数据通过 Linux framebuffer (/dev/fb0) 直接写入显存在板载 LCD 上显示。PC 端作为 TCP Server 接收帧头和帧数据后, 根据 pixfmt 自动选择颜色转换管线 (支持 4 种 RGB565 变体和 4 种 YUV 4:2:2 变体), 保存 raw 文件和可查看的 PPM 图片, 并通过 SDL2 窗口实时预览, 支持按键切换 8 种解码格式。

## 3.2 驱动层、内核层、应用层之间的关系

**应用层 (本项目)**:
- `v4l2_capture.c`: 通过 ioctl 系统调用与内核 V4L2 框架交互
- `fb_display.c`: 通过 ioctl 和 mmap 与内核 framebuffer 框架交互
- `tcp_socket.c`: 通过 socket 系统调用与内核 TCP/IP 协议栈交互

**内核层**:
- `mx6s_capture` 驱动 (文件 mx6s_capture.c, 驱动名 `mx6s-csi`, compatible `fsl,imx6s-csi`): 负责 i.MX6ULL CSI 控制器的 V4L2 实现, 暴露 `/dev/video1`。本项目对其做过 bring-up 修改 (默认格式初始化、并行接口 SOF 启动时序、BIT_SWAP16_EN 验证参数)
- `ov5640` 传感器驱动 (文件 ov5640.c, 模块名 `ov5640`): 通过 I2C 配置传感器寄存器。本项目修改过 s_stream/s_power 生命周期、格式寄存器设置顺序、MCLK 引脚复用
- Framebuffer 驱动: 暴露 `/dev/fb0`
- TCP/IP 协议栈: socket 层

**关系**:
- 应用层不直接与传感器通信 (I2C 由内核驱动完成)
- 应用层通过 V4L2 ioctl 间接控制传感器格式
- 内核驱动在内部完成 CSI DMA → 用户空间 mmap buffer 的数据搬运

## 3.4 TCP 报文从发送到接收全过程

### 发送端 (imx6ull_sender.c:273-300)

```
每帧循环:
  1. v4l2_get_frame() → 获取 mmap 指针 data, size (mapped kernel buffer)
  2. 构造 frame_header (栈变量):
     - hdr.magic = FRAME_MAGIC (0x12345678)
     - hdr.pixfmt = header_pixfmt (可能被 --yuv-order 覆盖)
     - 来源: ctx.pixfmt (S_FMT 驱动返回)
  3. send_frame_header(sockfd, &hdr):
     - 逐个字段 htonl() 转换为网络字节序
     - send_all() 发送 40 字节帧头
  4. send_all(sockfd, data, size):
     - 直接从 mmap 区域发送原始像素数据 (零拷贝)
  5. v4l2_put_frame() → QBUF 归还 buffer 给驱动
```

### 接收端 (pc_receiver.c:333-368)

```
每帧循环:
  1. recv_all(cfd, &n, 40) → 接收原始帧头 (网络字节序)
  2. ntohl() 逐字段转换为主机字节序
  3. 检查 hdr.magic != FRAME_MAGIC → 断开
  4. realloc 确保接收缓冲区 ≥ hdr.size
  5. recv_all(cfd, fbuf, hdr.size) → 接收帧数据
  6. 确定显示 pixfmt (优先级: g_disp_override > g_yuv_order > hdr.pixfmt)
  7. SDL 显示 (如果启用):
     - convert_line_to_rgb888() 逐行转换
     - SDL_UpdateTexture + SDL_RenderCopy + SDL_RenderPresent
  8. 文件保存:
     - save_raw_frame() → raw 文件
     - save_frame_as_ppm() → PPM (与 SDL 使用相同解码器)
```

# 5. 核心技术实现

## 5.1 V4L2 MMAP 采集 (v4l2_capture.c)

### 关键技术点

**1. xioctl EINTR 重试封装** ([v4l2_capture.c:31-41](src/v4l2_capture.c#L31-L41))
```c
int xioctl(int fd, int request, void *arg) {
    int ret;
    for (;;) {
        ret = ioctl(fd, request, arg);
        if (ret == -1 && errno == EINTR) continue;  // 信号中断, 重试
        return ret;
    }
}
```
这是所有 V4L2 项目中都会用到的标准模式, 防止被信号 (如 SIGCHLD) 意外中断。

**2. S_FMT 驱动返回值处理** ([v4l2_capture.c:92-160](src/v4l2_capture.c#L92-L160))

项目中最重要的设计决策之一。针对 mx6s-csi (mx6s_capture) 驱动的 G_FMT 不可靠问题:
- G_FMT 仅用于读取初始值 (可能返回 pixelformat=0/bytesperline=0)
- S_FMT 返回值为最终格式 (最可靠的格式来源)
- 格式不匹配不再是 fatal error (改为 WARN + 使用 S_FMT 返回值)
- imx6ull_sender 端额外检查 (行 208-217) 可在主循环前强制退出

**3. MMAP buffer 管理** ([v4l2_capture.c:187-219](src/v4l2_capture.c#L187-L219))

标准 V4L2 MMAP 流程:
- QUERYBUF 获取每个 buffer 的 offset 和 length
- mmap 映射到用户空间 (PROT_READ|PROT_WRITE, MAP_SHARED)
- QBUF 将空 buffer 入队
- STREAMON 启动视频流

**4. poll + DQBUF 帧获取** ([v4l2_capture.c:252-306](src/v4l2_capture.c#L252-L306))

超时处理: poll 2s 超时 → 返回 -ETIMEDOUT (非致命)
DQBUF EAGAIN → 返回 -EAGAIN (非致命)
调用者在循环中 continue 重试

**5. 错误回滚** ([v4l2_capture.c:235-246](src/v4l2_capture.c#L235-L246))

fail_map 标签会 munmap 所有已成功 mmap 的 buffer
fail 标签会 close fd

### 初始化流程 ([fb_display.c:29-127](src/fb_display.c#L29-L127))

### YUYV→XRGB8888 软件转换 ([fb_display.c:137-158](src/fb_display.c#L137-L158))

使用 ITU-R BT.601 定点转换公式 (避免浮点), C=Y-16 (C<0 取 0):
```
R = (298*(Y-16) + 409*(V-128) + 128) >> 8
G = (298*(Y-16) - 100*(U-128) - 208*(V-128) + 128) >> 8
B = (298*(Y-16) + 516*(U-128) + 128) >> 8
```
clamp [0,255], 按 var.red/green/blue.offset 通用打包为 32 位像素 (0x00RRGGBB)。RGB565 输入分支逐像素解包 + 5/6bit 位扩展后同样输出 XRGB8888。

### 行步长与写入方式 ([fb_display.c:179-271](src/fb_display.c#L179-L271))

- 目标行首地址 = `fb_mmap + (dst_y+row) * fb->line_length` (必须用 fix.line_length, 不能假设 = width*4); 每像素写 uint32_t, 像素偏移 = dst_x*4
- 源行步长 = V4L2 的 ctx.bytesperline (接口参数 src_stride), 避免驱动行尾 padding 导致错行

### 居中/裁剪逻辑 ([fb_display.c:293-311](src/fb_display.c#L293-L311))

```
图像 ≤ 屏幕: copy_w=width, src_x=0, dst_x=(scr_w-width)/2  (居中)
图像 > 屏幕: copy_w=scr_w, src_x=(width-scr_w)/2, dst_x=0  (裁剪)
```

# 6. 并发、内存与异常处理

## 6.1 并发分析

### 单线程架构

**imx6ull_sender** 和 **pc_receiver** 都是单线程、事件驱动模式:
- 采集循环在 main() 中串行执行
- poll() 等待帧就绪 (阻塞但可中断)
- 信号处理只设置 `volatile sig_atomic_t g_running` (imx6ull_sender.c:29, pc_receiver.c:35)
- **不存在多线程竞争**

### 信号处理与主循环

```
主循环: while (g_running && ...) { ... }
信号:    SIGINT/SIGTERM → signal_handler() → g_running = 0
```

风险评估:
- g_running 是 `volatile sig_atomic_t` (使用 sig_atomic_t 保证在信号处理中原子读/写)
- 不涉及复杂共享数据结构, 仅用于退出标志
- **风险等级: 低, 实现正确**

### mmap buffer 共享

V4L2 mmap buffer 在内核驱动和应用层之间共享:
- 驱动写入 (DMA), 应用层读取 (v4l2_get_frame 返回指针)
- 同步机制: DQBUF (获取所有权) → 应用读取 → QBUF (归还所有权)
- **正确使用了 V4L2 提供的同步原语, 不存在竞态**

# 7. 调试与问题解决

## 7.1 问题: mx6s-csi (mx6s_capture) 驱动的 G_FMT 返回 pixelformat=0

**现象**: v4l2_init 中 S_FMT 之后调用 G_FMT 读取当前格式, 但 G_FMT 返回 pixelformat=0, bytesperline=0, 导致后续逻辑误以为格式无效。

**排查过程**: 
1. 在 v4l2_init 中 G_FMT 后打印返回值 (v4l2_capture.c:100-104)
2. 发现 G_FMT 设置 pixfmt 不报错但返回零值
3. 通过 v4l2_format_test.c 工具独立测试 TRY_FMT→S_FMT→G_FMT 流程
4. 确认 S_FMT 返回值正确但 G_FMT 返回无效值 (tools/v4l2_format_test.c:236-249)

**根因** (已从驱动源码确认): `mx6s_capture.c` 的 `mx6s_vidioc_g_fmt_vid_cap()` 只是把 `csi_dev->pix` 原样拷回 (行 1612), 而原始驱动的 probe 从不初始化 `csi_dev->pix` —— 只有 S_FMT 才填充它。因此在 S_FMT 之前调用 G_FMT, 会得到全零的 pixelformat / bytesperline。这是原厂驱动的缺陷, 不是时序偶发问题。

**修改位置**:
- v4l2_capture.c: 不再用 G_FMT 覆盖 S_FMT 结果 (行 134-142 注释说明)
- v4l2_capture.c: G_FMT 失败只 WARN, 不 fatal (行 100-104)
- v4l2_format_test.c: 增加 G_FMT 无效值检测和警告 (行 237-248)
- mx6s_capture.c: probe 中初始化默认格式 YUYV 640x480 (行 2002-2013), 保证 G_FMT 在 S_FMT 前也返回有效值 (驱动侧修复)

**验证结果**: S_FMT 返回值路径稳定, 采集正常工作。文档确认 "Use S_FMT result as the actual format"。

## 7.2 问题: i.MX6ULL CSI R/B 通道交换导致颜色偏蓝

**现象**: RGB565 格式下 PC 端 SDL 显示和 PPM 文件颜色异常 (红色偏蓝/蓝色偏红)。

**排查过程**:
1. 用已知正确颜色的测试图像确认问题出在采集端而非显示端
2. 对比标准 RGB565 和 R/B 交换后的 BGR565 显示效果
3. 在 PC 端添加 --swap-rb / --display-format bgr565 参数进行对比测试
4. 确认 BGR565_LE 解码器给出正确颜色

**根因**: 本项目 OV5640 走的是 8-bit 并行 DVP 总线 (i.MX6ULL 芯片没有 MIPI CSI 控制器)。RGB565 每像素 2 字节, 在 8-bit 总线上逐字节传输: byte0={g[2:0],b[4:0]}, byte1={r[4:0],g[5:3]} (ov5640.c:2864 注释)。CSI 控制器把两个 8-bit 传输打包为 16-bit 字时, 字节顺序与标准 RGB565 LE 相反 —— 交换两个字节后得到的恰好等价于 BGR565, 这就是观察到的 "R/B 交换" 现象。硬件侧有对应修法: CSICR1 bit31 (BIT_SWAP16_EN) 可交换每个 16-bit 字的两个字节, 已在驱动中通过新增模块参数 `csi_rgb565_swap16` 验证 (mx6s_capture.c:160-162, 867-877)。本项目最终保留应用层 BGR565 解码方案。

**修改位置**:
- frame_proto.h: 增加 PIX_FMT_BGR565 / PIX_FMT_BGR565X 自定义 FOURCC (行 40-41)
- pc_receiver.c: 增加 bgr565_le_to_rgb888_line 和 bgr565_be_to_rgb888_line 函数 (行 53-61)
- pc_receiver.c: 增加 --swap-rb 命令行参数 (行 303)
- pc_receiver.c: SDL 按键 3/4 切换到 BGR565 (行 167-168)
- README: 在诊断流程中记录 BGR565 推荐 (README Step 3 诊断)
- mx6s_capture.c: 新增 csi_rgb565_swap16 模块参数, 用 BIT_SWAP16_EN 做硬件侧字节交换验证 (行 160-162, 867-877)

**验证结果**: BGR565_LE 解码器颜色正确, 设为默认推荐格式。

## 7.3 问题: YUV 字节顺序不确定

**现象**: YUYV 格式采集, 但 PC 端颜色偏紫/偏绿, 怀疑 YUV 字节顺序与实际数据不匹配。

**排查过程**:
1. YUYV 4:2:2 的 4 种常见字节顺序: YUYV, UYVY, YVYU, VYUY
2. 在 PC 端实现全部 4 种解码器 (pc_receiver.c:80-90)
3. 在 PC 端增加 SDL 按键 5-8 实时切换 (行 169-172)
4. 在发送端增加 --yuv-order 参数 (imx6ull_sender.c:149-157)

**根因**: 驱动层进一步确认了两点: (1) ov5640 的 `ov5640_change_mode()` 会整表下载模式寄存器, 把格式寄存器 0x4300/0x501f 覆盖回 YUYV 默认值 (0x4300=0x30), 原 `s_fmt` "先设格式、后切模式" 的顺序导致传感器实际输出格式与 S_FMT 声称的不一致; (2) 因此 S_FMT 返回 YUYV 不保证传感器寄存器状态与之相符。驱动已修复为 "先切模式、再设格式" (ov5640_s_fmt Step1/Step2), 并在 s_parm 末尾重新应用格式 (见第 7.6 节)。

**修改位置**:
- frame_proto.h: 增加 PIX_FMT_YVYU / PIX_FMT_VYUY (行 42-43)
- imx6ull_sender.c: 增加 --yuv-order 参数 (行 53-60, 149-157)
- pc_receiver.c: 增加 --yuv-order 参数和 g_yuv_order 全局变量 (行 304)
- pc_receiver.c: 增加 yvyu_to_rgb888_line, vyuy_to_rgb888_line (行 86-90)
- ov5640.c: s_fmt 重排为 "先切模式再设 0x4300/0x501f" (行 2980-3000); s_parm 后重新应用格式 (行 2810-2822)

**验证结果**: 通过按键切换可以确认正确的字节顺序, YUV 颜色正常。

## 7.5 问题: CSI 并行接口启动时序 (SOF 同步)

**现象**: 并行 DVP 接口下, STREAMON 后前几帧错位/花屏, 或出现 Rx FIFO overflow 中断。

**排查过程**: 对比驱动中 MIPI 分支 (CSI 使能后立即开 DMA+中断) 与并行分支的差异, 在 start_streaming 各步骤加日志定位帧数据从哪一步开始异常。

**根因**: 并行接口下, 若在传感器输出帧之前就使能 DMA 请求, CSI 会收到无帧同步的数据 (传感器此时还未稳定输出), 导致帧错位。需要在第一帧 SOF 到来时再做 DMA reflash 并开启 DMA 请求与中断。

**修改位置**:
- mx6s_capture.c: `mx6s_csi_setup()` 并行分支只做软件复位, 不开 DMA/中断 (行 731-754)
- mx6s_capture.c: 新增 `mx6s_csi_wait_sof()` —— 传感器 s_stream(1) 后轮询 CSISR 的 BIT_SOF_INT, 收到 SOF 后执行 DMA reflash, 再开启 DMA 请求 + 中断 + CSI 使能 (行 761-808)
- mx6s_capture.c: `mx6s_start_streaming()` 重排为 setup → s_stream(1) → wait_sof 三步 (行 975-1005)

**验证结果**: dmesg 可见 "waiting for SOF... / SOF received after N iterations / CSI DMA and interrupts enabled" 日志, 并行接口采集稳定。

## 7.6 问题: ov5640 格式寄存器被模式表覆盖 (0x4300/0x501f)

**现象**: S_FMT 设置 RGB565/JPEG 后实际输出仍是 YUYV; S_PARM 切换帧率后格式又回退成 YUYV。

**根因**: `ov5640_change_mode()` 整表下载模式寄存器, 模式表中包含 `{0x4300, 0x30}` (YUV422), 会覆盖 `ov5640_set_framefmt()` 刚写入的格式寄存器 0x4300/0x501f。原代码顺序是 "先 set_framefmt、后 change_mode", 格式必然丢失; s_parm 中只调 change_mode 不再设格式, 同样被覆盖。

**修改位置**:
- ov5640.c: `ov5640_s_fmt()` 重排为 Step1 先切分辨率模式、Step2 再设 0x4300/0x501f 格式寄存器 (行 2980-3000)
- ov5640.c: `ov5640_s_parm()` 在 change_mode 之后重新调用 ov5640_set_framefmt 刷回当前格式 (行 2810-2822)
- ov5640.c: probe 中强制默认 YUYV 并读回 0x4300/0x501f 验证 (行 3341-3367)

**验证结果**: pr_info 读回日志显示 0x4300/0x501f 与 S_FMT 请求一致, 格式切换不再回退。

## 7.7 问题: 驱动 TRY_FMT 违反 V4L2 语义 + 格式 fallback 空指针

**现象**: (1) 应用层调 VIDIOC_TRY_FMT (本应只查询不改硬件) 后传感器寄存器真的变了; (2) S_FMT 传入驱动不支持的 mbus code 后, 后续 G_FMT 在用户态或驱动内崩溃。

**根因**: (1) 驱动 try_fmt 路径错误地调用了 `v4l2_subdev_call(sd, video, s_mbus_fmt, ...)` 而非 `try_mbus_fmt` —— TRY_FMT 被做成有副作用; (2) ov5640 s_fmt 对不支持的 code fallback 到 RGB565 时, `sensor->fmt` 未同步赋值, 后续 g_fmt 解引用 NULL。另外原厂驱动 MIPI 分支存在 bitmask 语义错误: `cr18 &= BIT_MIPI_DATA_FORMAT_MASK` 应为 `cr18 &= ~BIT_MIPI_DATA_FORMAT_MASK` (前者清掉了掩码之外的全部位)。该分支在 i.MX6ULL 并行路径上不触发, 属顺带修复。

**修改位置**:
- mx6s_capture.c: try_fmt 改调 try_mbus_fmt (行 1521), MIPI bitmask 修复 (行 888)
- ov5640.c: s_fmt fallback 时显式 `fmt = &ov5640_colour_fmts[0]; mf->code = fmt->code` (行 2971-2976)

**验证结果**: TRY_FMT 无副作用; 传非法格式不再崩溃, 自动回落到 RGB565。

## 7.8 问题: OV5640 闪光灯常亮 (MCLK 引脚与 LED 共用)

**现象**: 加载 mx6s_capture / ov5640 驱动后板载闪光灯 LED 一直亮, 应用退出、rmmod 后仍不灭。

**排查过程**: 发现闪光灯 LED 物理连接在 CSI_MCLK 引脚 (高电平亮), 用 devmem 手动切换 IOMUXC 验证思路, 最终确认三层根因叠加:
1. **DTS 层**: CSI_MCLK pad 配置 0x1b088 (PUS=10 → 100K 上拉), MCLK 关闭时引脚浮空被拉高
2. **驱动层**: `mx6s_csi_deinit()` 先 `csihw_reset` (关 MCLKEN) 又调用 `csi_init_interface` (重新打开 MCLKEN)
3. **硬件层**: CCM 时钟关闭后 CSI MCLK 输出级仍使能, 引脚恒高, 100K 下拉压不住

**修改位置**:
- DTS (imx6ull-alientek-emmc.dts): CSI_MCLK pad 0x1b088 → 0x13088 (PUS=00 → 100K 下拉)
- mx6s_capture.c: 删除 deinit 中多余的 csi_init_interface 调用 (行 717-722)
- ov5640.c: 新增 `mclk_pin_to_gpio_low()` / `mclk_pin_to_csi_mclk()`, 不用 MCLK 时把引脚从 ALT0(CSI_MCLK) 切到 ALT5(GPIO4_IO17) 输出低 (行 155-200)
- ov5640.c: 新增 s_stream 回调 (0x3008: 0x02 工作 / 0x42 软件待机), s_power 中加引脚切换 (行 2679-2701, 3136-3163)
- ov5640.c: probe 末尾关 STROBE (0x3018=0x00) + 软件待机 + 切 GPIO 低 (行 3369-3378)

**验证结果**: LED 仅在采流 (MCLK 输出 24MHz) 时亮, 其余阶段全灭。详见 /home/why/Log/ov5640-flash-fix-changelog.md。

## 7.9 问题: 板端 LCD 显示泛绿 (fb0 实为 32bpp XRGB8888)

**现象**: `-l` 启用 LCD 显示时画面泛绿、像素错位、行间花屏。

**根因**: /dev/fb0 实际是 32bpp XRGB8888 (1024×600, line_length=4096, red.offset=16/green.offset=8/blue.offset=0), 但原代码按 16bpp RGB565 屏假设写入:

**修改位置**:

- fb_display.h / fb_display.c / imx6ull_sender.c: `fb_display_show_frame()` 增加 src_stride 参数, 调用点传 `ctx.bytesperline` (行 273, sender 行 271-274)

**验证结果**: make arm 零警告; 板端 LCD 颜色正常, 居中显示; TCP 帧内容不受影响。

| "从零开发了摄像头驱动" | 实际是修改/适配内核树中已有的 mx6s_capture.c / ov5640.c (修复 6+ 个驱动 bug + MCLK 引脚管理, 见 7.5-7.8、8.2), 可表述为 "修改/适配内核 CSI 与 OV5640 驱动" |

# 10. 面试问题

## 10.1 20 道基础追问题

**Q1**: V4L2 采集的标准流程是什么? 每一步的 ioctl 命令是什么?
> **答案**: open → VIDIOC_QUERYCAP → VIDIOC_S_FMT / VIDIOC_G_FMT → VIDIOC_REQBUFS (count) → VIDIOC_QUERYBUF (×count) → mmap (×count) → VIDIOC_QBUF (×count) → VIDIOC_STREAMON → 循环: poll + VIDIOC_DQBUF → VIDIOC_STREAMOFF → munmap → close。见 [v4l2_capture.c:49-247](src/v4l2_capture.c#L49-L247)。

**Q2**: 为什么要用 MMAP 而不是 READ/WRITE 方式?
> **答案**: MMAP 避免内核空间到用户空间的内存拷贝 (零拷贝), 适合高帧率视频。READ 每次将数据从内核 buffer 拷贝到用户 buffer, 性能开销大。本项目中 v4l2_init 使用 V4L2_MEMORY_MMAP ([v4l2_capture.c:165](src/v4l2_capture.c#L165))。

**Q3**: xioctl 为什么要封装 EINTR 重试?
> **答案**: ioctl 可能被信号 (如 SIGCHLD) 中断, 返回 -1 且 errno=EINTR。直接 fail 会导致偶发性失败。见 [v4l2_capture.c:31-41](src/v4l2_capture.c#L31-L41)。

**Q4**: S_FMT 和 G_FMT 的区别是什么? 本项目为什么以 S_FMT 为准?
> **答案**: S_FMT 设置格式并返回实际支持的参数; G_FMT 读取当前格式。Linux 4.1.15 的 mx6s-csi (mx6s_capture.c) 驱动 G_FMT 可能返回 pixelformat=0 / bytesperline=0 (无效值), 故不能依赖 G_FMT。根因已从驱动源码确认: G_FMT 只是返回 csi_dev->pix, 而原驱动 probe 从不初始化它, 只有 S_FMT 才填充。本项目双层修复: 驱动侧 probe 初始化默认格式 (mx6s_capture.c:2002-2013), 应用层以 S_FMT 返回值为准 ([v4l2_capture.c:134-142](src/v4l2_capture.c#L134-L142))。

**Q5**: REQBUFS 的 count 参数是什么含义?
> **答案**: 请求驱动的缓冲区数量。本项目请求 3 个 buffer, 实际分配数量由驱动返回 ([v4l2_capture.c:166-174](src/v4l2_capture.c#L166-L174))。3 个 buffer 是最小值, 1 个正在采集, 1 个正在 DQBUF, 1 个正在 QBUF。

**Q6**: poll 在 V4L2 采集中的作用是什么? 为什么需要 poll?
> **答案**: poll 等待驱动填充 buffer 完成 (POLLIN 事件), 避免忙等。使用 O_NONBLOCK 模式时, 没有 poll 直接 DQBUF 会返回 EAGAIN。见 [v4l2_capture.c:259-272](src/v4l2_capture.c#L259-L272)。

**Q7**: send_all/recv_all 为什么要自己实现而不是直接用 send/recv?
> **答案**: TCP 是流协议, 单次 send/recv 不保证发送/接收完整数据。send_all/recv_all 用 while 循环确保精确传输指定长度。见 [tcp_socket.c:30-78](src/tcp_socket.c#L30-L78)。

**Q8**: 网络字节序转换在项目中的具体位置在哪里?
> **答案**: 发送端: imx6ull_sender.c:62-79 中 htonl 逐字段转换; 接收端: pc_receiver.c:222-229 中 ntohl 转换。timestamp_us 需要拆分 64 位分别转换。

**Q9**: RGB565 到 RGB888 的位扩展是怎么做的? 为什么用这种算法?
> **答案**: `r8 = (r5 << 3) | (r5 >> 2)` 等。左移填高位, 右移填低位, 实现更平滑的渐变。如果只用 `r5 << 3`, 最大值 0xF8 < 0xFF, 永远达不到纯白。见 [pc_receiver.c:44-46](src/pc_receiver.c#L44-L46)。

**Q10**: YUV→RGB 的 BT.601 公式是什么? 为什么用定点运算?
> **答案**: `R=(298*(Y-16)+409*(V-128)+128)>>8` 等, C=Y-16 小于 0 时取 0。定点运算避免浮点, 适合 ARM Cortex-A7 无硬件浮点单元或性能受限场景。见 [fb_display.c:137-158](src/fb_display.c#L137-L158)。

**Q11**: framebuffer 的 mmap 和 V4L2 的 mmap 有什么异同?
> **答案**: 都是 mmap 将内核内存映射到用户空间, 但用途不同: V4L2 mmap 映射驱动分配的 DMA buffer (环形缓冲区); framebuffer mmap 映射显存 (framebuffer), 直接写像素。见 [fb_display.c:93-114](src/fb_display.c#L93-L114)。

**Q12**: 程序如何实现优雅退出?
> **答案**: 注册 SIGINT/SIGTERM 信号处理器, 设置 `volatile sig_atomic_t g_running=0`, 主循环检查 g_running 后执行 STREAMOFF→munmap→close。见 [imx6ull_sender.c:29-36, 251, 313-318](src/imx6ull_sender.c#L29-L36)。

**Q13**: 为什么 imx6ull_sender 和 pc_receiver 都是单线程的?
> **答案**: 采集-发送和接收-显示都是串行数据流, 单线程避免锁开销。如需并行 (如采集和发送分离), 可以用多线程, 但本项目数据路径简单, 单线程足够。见 [imx6ull_sender.c:251-309](src/imx6ull_sender.c#L251-L309)。

**Q14**: SDL2 纹理更新为什么使用 Streaming access?
> **答案**: SDL_TEXTUREACCESS_STREAMING 适合每帧更新的动态纹理, 允许 UpdateTexture 逐行更新, 减少内存分配。见 [pc_receiver.c:148](src/pc_receiver.c#L148)。

**Q15**: Makefile 中 ARM_CC 和 PC_CC 分开定义的原因?
> **答案**: 板端需要交叉编译 (arm-linux-gnueabihf-gcc), PC 端用本机 gcc。同一个 Makefile 通过不同目标 (arm/pc) 选择不同编译器。见 [Makefile:25-29](Makefile#L25-L29)。

**Q16**: 为什么工具程序 (tools/) 独立编译, 不依赖 v4l2_capture.c?
> **答案**: 诊断工具需要在问题出现时独立运行, 不依赖采集库的状态。工具自包含 xioctl 和所有 ioctl 调用, 减少依赖链路。见 [tools/v4l2_info.c:73-82](tools/v4l2_info.c#L73-L82)。

**Q17**: MSG_NOSIGNAL 标志的作用是什么?
> **答案**: 防止对已关闭的 socket 发送数据时产生 SIGPIPE 信号导致程序退出。见 [tcp_socket.c:37](src/tcp_socket.c#L37)。

**Q18**: O_NONBLOCK 模式对本项目的影响?
> **答案**: open 设备时使用 O_NONBLOCK, DQBUF 在无帧就绪时返回 EAGAIN 而非阻塞。需要配合 poll 使用。见 [v4l2_capture.c:62](src/v4l2_capture.c#L62)。

**Q19**: 项目中 YUV 4:2:2 的 4 种字节顺序有什么区别?
> **答案**: 每 4 字节表示 2 个像素, 区别在于 Y/U/V 的排列: YUYV=Y0,U,Y1,V; UYVY=U,Y0,V,Y1; YVYU=Y0,V,Y1,U; VYUY=V,Y0,U,Y1。见 [pc_receiver.c:80-90](src/pc_receiver.c#L80-L90)。

**Q20**: BGR565 和 RGB565 的区别是什么? 项目为什么需要 BGR565?
> **答案**: BGR565 将 RGB565 的 R 和 B 通道交换。本项目 OV5640 走 8-bit 并行 DVP, RGB565 每像素 2 字节逐字节传输, CSI 打包 16-bit 字时字节序与标准 RGB565 LE 相反, 交换字节后等价于 BGR565, 所以 PC 端需要 BGR565 解码器。硬件侧也有修法: CSICR1 bit31 (BIT_SWAP16_EN) 交换每个 16-bit 字的两个字节, 驱动里加了 csi_rgb565_swap16 参数验证过。见 [pc_receiver.c:53-56](src/pc_receiver.c#L53-L56)。

## 10.2 20 道源码细节题

**Q21**: `v4l2_context` 结构体有哪些字段? 分别在哪个函数中被赋值?
> **答案**: fd, nbufs, buf_mmap[8], buf_len[8], width, height, pixfmt, bytesperline, sizeimage。在 v4l2_init() 中赋值 ([v4l2_capture.c:138-142](src/v4l2_capture.c#L138-L142)): ctx->fd (行 62), nbufs (行 174), buf_mmap/buf_len (行 201-212), width/height/pixfmt/bytesperline/sizeimage (行 138-142)。

**Q22**: `frame_header` 有多少字节? 每个字段的大小是多少?
> **答案**: 40 字节: 8 个 uint32_t (4B×8=32) + 1 个 uint64_t (8B) = 40B。定义见 [frame_proto.h:48-58](include/frame_proto.h#L48-L58)。

**Q23**: `v4l2_init` 中有几个 goto 标签? 分别对应什么错误路径?
> **答案**: 3 个: fail_fd (open 失败, 直接返回), fail (QUERYCAP/S_FMT/REQBUFS 失败, close fd), fail_map (QUERYBUF/mmap/QBUF/STREAMON 失败, munmap 已成功的 buffer 后 close fd)。见 [v4l2_capture.c:235-246](src/v4l2_capture.c#L235-L246)。

**Q24**: `fb_display_show_frame` 如何处理图像尺寸和屏幕尺寸不匹配?
> **答案**: 图像 ≤ 屏幕 → 居中 (dst_x=(scr_w-width)/2); 图像 > 屏幕 → 裁剪 (src_x=(width-scr_w)/2)。见 [fb_display.c:293-311](src/fb_display.c#L293-L311)。

**Q25**: `fb_copy_yuyv_to_xrgb8888` 中 YUYV 的 U 和 V 是如何从源数据中取出的?
> **答案**: YUYV 每 4 字节 = [Y0, U, Y1, V], 2 个像素共享 U V。pair_off = (px/2)*4, y0=src[pair_off+0], u=src[pair_off+1], y1=src[pair_off+2], v=src[pair_off+3], 奇偶像素分别用 y1/y0, 再经 BT.601 定点公式转 RGB888。见 [fb_display.c:250-266](src/fb_display.c#L250-L266)。

**Q26**: `imx6ull_sender` 中 `header_pixfmt` 的赋值逻辑是什么?
> **答案**: `header_pixfmt = (yuv_override && pixfmt_is_yuv422(ctx.pixfmt)) ? yuv_override : ctx.pixfmt`. 即: 如果设置了 --yuv-order 且 S_FMT 返回 YUV 格式, 用覆盖值; 否则用 ctx.pixfmt。见 [imx6ull_sender.c:275-276](src/imx6ull_sender.c#L275-L276)。

**Q27**: PC 端 `recv_frame_header` 如何解析 timestamp_us?
> **答案**: 拆分高 32 位和低 32 位分别 ntohl 后拼回 64 位: `(((uint64_t)ntohl(hi32))<<32) | ntohl(lo32)`. 见 [pc_receiver.c:227](src/pc_receiver.c#L227)。

**Q28**: `pc_receiver` 中 `g_disp_override` 和 `g_yuv_order` 的优先级关系是什么?
> **答案**: g_disp_override (键盘/命令行覆盖) > g_yuv_order (--yuv-order) > hdr.pixfmt (帧头自动检测). 判断逻辑见 [pc_receiver.c:187-192](src/pc_receiver.c#L187-L192)。

**Q29**: `v4l2_format_test.c` 如何判断 G_FMT 返回值无效?
> **答案**: 两个条件: `g_pixfmt == 0` 或 `fmt.fmt.pix.bytesperline == 0`. 见 [tools/v4l2_format_test.c:237](tools/v4l2_format_test.c#L237)。

**Q30**: 项目中哪些文件需要用到 `<arpa/inet.h>`? 分别用于什么函数?
> **答案**: imx6ull_sender.c (htonl), pc_receiver.c (ntohl), tcp_socket.c (htons, inet_aton/gethostbyname)。用途: 网络字节序转换和地址解析。

**Q31**: Makefile 中 `install` 目标安装哪些文件? 安装到哪里?
> **答案**: ARM_BINS (imx6ull_sender) + ARM_TOOLS (v4l2_info, v4l2_format_test), 安装到 `/home/why/zdyz/nfs/rootfs/lib/modules/4.1.15`. 见 [Makefile:168-173](Makefile#L168-L173)。

**Q32**: `sdl_display_init` 中 SDL 初始化失败时的资源释放顺序是什么?
> **答案**: Window 失败 → SDL_Quit; Renderer 失败 → SDL_DestroyWindow + SDL_Quit; Texture 失败 → SDL_DestroyRenderer + SDL_DestroyWindow + SDL_Quit. 反向释放。见 [pc_receiver.c:145-149](src/pc_receiver.c#L145-L149)。

**Q33**: `pixfmt_is_displayable` 判断哪些格式可显示?
> **答案**: pixfmt_is_rgb_variant (RGB565/RGB565X/BGR565/BGR565X) 或 pixfmt_is_yuv422 (YUYV/UYVY/YVYU/VYUY). MJPEG 不可显示。见 [frame_proto.h:127-131](include/frame_proto.h#L127-L131)。

**Q34**: `v4l2_deinit` 中遍历 nbufs 时如何判断 buffer 是否已经 mmap?
> **答案**: 检查 `ctx->buf_mmap[i] != NULL && ctx->buf_mmap[i] != MAP_FAILED`. 见 [v4l2_capture.c:346](src/v4l2_capture.c#L346)。

**Q35**: `tcp_client_connect` 中 gethostbyname 的 fallback 逻辑是什么?
> **答案**: 先尝试 inet_aton 解析点分十进制 IP, 失败则 gethostbyname 进行 DNS 查询。gethostbyname 返回后检查 h_addrtype == AF_INET。见 [tcp_socket.c:98-113](src/tcp_socket.c#L98-L113)。

**Q36**: `v4l2_info.c` 中如何处理老内核缺少的 colorspace 常量?
> **答案**: 用 #ifndef 宏保护, 自行定义所有 9 种 colorspace 常量 (V4L2_COLORSPACE_SMPTE170M 到 V4L2_COLORSPACE_SRGB)。见 [tools/v4l2_info.c:45-71](tools/v4l2_info.c#L45-L71)。

**Q37**: imx6ull_sender 的 main 中信号注册在 V4L2 初始化之前还是之后? 为什么?
> **答案**: 之前 (行 184), 在 V4L2 init (行 189) 之前。确保初始化过程中如果收到 Ctrl+C 也能退出。但信号初始化失败不会影响程序逻辑。

**Q38**: 项目中有哪些函数返回 `-ETIMEDOUT` 或 `-EAGAIN`? 调用者如何处理?
> **答案**: v4l2_get_frame 返回 -ETIMEDOUT (poll 超时) 或 -EAGAIN (DQBUF 无帧)。调用者 (imx6ull_sender.c:261-263) 都是 continue 继续循环。

**Q39**: `fb_copy_yuyv_to_xrgb8888` 中为什么要对齐 src_x 到偶数?
> **答案**: YUYV 每 4 字节 = 2 像素, 奇像素和偶像素共用 U/V, 从奇数位置开始会导致 U/V 错位。`aligned_x = src_x & ~1U` 将起始位置对齐到偶数, 同时目标位置同步右移 delta (src_x-aligned_x) 保证裁剪画面不整体偏移, 并做屏幕右边界越界防护。见 [fb_display.c:231-243](src/fb_display.c#L231-L243)。

**Q40**: `pc_receiver` 的 main 中 `(void)size` 的作用是什么?
> **答案**: 在 save_frame_as_ppm 中参数 size 在当前实现中未使用 (PPM 总是按 width*height*2 计算)。(void)size 抑制编译器 -Wunused-parameter 警告。见 [pc_receiver.c:113](src/pc_receiver.c#L113)。

## 10.3 10 道故障排查题

**Q41**: 板端运行 imx6ull_sender 后, PC 端收不到任何数据, 如何排查?
> **参考答案**: 
> 1. 确认网络连通性: `ping <PC_IP>` (板端)
> 2. 确认 PC 端先启动: `./pc_receiver -p 5000`
> 3. 确认板端日志: 查看 [INFO] 输出, 确认 TCP connect 成功
> 4. 确认摄像头正常: `./v4l2_info /dev/video1` 检查设备
> 5. 检查防火墙: `sudo ufw status` 确认端口 5000 放行
> 6. 用 netcat 测试: PC 端 `nc -l 5000 > test.bin`, 板端发送少量帧

**Q42**: PC 端 SDL 显示颜色偏蓝/偏红, 如何排查和解决?
> **参考答案**:
> 1. 按键盘 `3` 切换到 BGR565_LE (i.MX6ULL CSI R/B 交换的推荐模式)
> 2. 尝试 `1`(RGB565), `2`(RGB565X_BE), `4`(BGR565X_BE) 依次测试
> 3. 如果是 YUV 格式, 尝试 `5-8` 切换 YUV 字节顺序
> 4. 如果 PPM 文件也异常, 说明是解码格式问题; 如果 PPM 正常但 SDL 异常, 检查显示器设置
> 5. 用 `--display-format bgr565` 命令行参数固定解码格式
> 6. 运行 `./v4l2_format_test` 诊断板端格式协商

**Q43**: v4l2_init 返回 -1, 日志显示 "STREAMON failed", 可能是什么原因?
> **参考答案**:
> 1. 摄像头排线未连接或松动
> 2. 传感器未上电 (XCLK 未输出)
> 3. I2C 通信失败 (传感器未检测到)
> 4. 设备树 pinctrl 配置错误
> 5. 内核驱动未加载: `lsmod | grep ov5640` + `dmesg | grep ov5640`
> 6. CSI 时钟配置不正确
> 7. CSI_MCLK 引脚被切到 GPIO (本项目 MCLK 与闪光灯 LED 共用引脚, 引脚功能切换错误时传感器无时钟)
> 8. 并行接口下驱动 start_streaming 等 SOF 超时: dmesg 查 "timeout when wait for SOF" (mx6s_csi_wait_sof)
> 错误位置: [v4l2_capture.c:224-228](src/v4l2_capture.c#L224-L228)

**Q44**: poll 持续超时 (2000ms), 日志重复 "[WARN] poll timeout", 什么原因?
> **参考答案**:
> 1. STREAMON 后传感器需要预热几帧, 刚开始几次超时正常
> 2. 连续超时说明传感器没有输出帧数据
> 3. 检查 dmesg 是否有 CSI 中断错误 / 驱动日志 ("waiting for SOF..." 是否出现)
> 4. 确认设备树 csi_id 和 mux_id 配置正确
> 5. 确认 CSI_MCLK 引脚功能正确 (本项目与闪光灯 LED 共用, 被切到 GPIO 时无 MCLK)
> 6. 摄像头是否被其他进程占用: `fuser /dev/video1`
> 相关代码: [v4l2_capture.c:269-271](src/v4l2_capture.c#L269-L271)

**Q45**: PC 端收到乱码或魔数检查失败, "[ERROR] Bad magic", 怎么排查?
> **参考答案**:
> 1. 检查是否有其他程序也连接了同一端口
> 2. 确认发送端和接收端字节序一致 (都用 htonl/ntohl)
> 3. 检查 recv_all 是否正确接收 (部分接收导致后续帧头对齐错误)
> 4. 检查网络中是否有中间设备修改数据
> 5. 用 tcpdump 抓包检查: `sudo tcpdump -i eth0 -X port 5000`
> 相关代码: [pc_receiver.c:337](src/pc_receiver.c#L337)

**Q46**: PPM 文件可以打开但图像是灰的 ([rgb] 全是 0x80), 什么原因?
> **参考答案**:
> 1. 像素格式不被 convert_line_to_rgb888 支持, 走了 default 分支 → memset(0x80)
> 2. 检查 frame_header 中的 pixfmt 字段值
> 3. 检查 save_frame_as_ppm 调用时传入的 epix 参数
> 4. 确认 pixfmt_is_displayable(epix) 返回 true
> 相关代码: [pc_receiver.c:104](src/pc_receiver.c#L104) (default 分支), [pc_receiver.c:363](src/pc_receiver.c#L363) (PPM 条件)

**Q47**: 交叉编译失败, "arm-linux-gnueabihf-gcc: command not found", 如何解决?
> **参考答案**:

> **参考答案**:

**Q49**: 板端运行时内存溢出 (OOM), 如何分析?
> **参考答案**:
> 1. V4L2 mmap buffer 大小 = sizeimage × nbufs (通常 3), 不会无限增长
> 2. framebuffer mmap = smem_len (固定), 不会增长
> 3. TCP Socket buffer 大小由内核管理, 用户态没有大缓冲区
> 4. 使用 `top` 或 `cat /proc/<pid>/status` 监控内存
> 5. 检查是否有 zram/swap 导致的性能下降
> 6. 项目本身的内存使用是固定的 (无动态增长), OOM 更可能来自其他进程

**Q50**: imx6ull_sender 的 -f 参数指定的格式和 S_FMT 实际返回不同, 程序如何处理?
> **参考答案**:
> 1. v4l2_init 内部: WARN 打印不匹配但继续使用 S_FMT 返回的实际格式 (v4l2_capture.c:153-160)
> 2. imx6ull_sender 外部检查: ctx.pixfmt != req_pixfmt → ERROR 打印 + v4l2_deinit + return 1 (imx6ull_sender.c:208-217)
> 3. 整体结果: 不匹配时程序退出而非使用错误格式, 要求用户选择驱动支持的格式
> 4. 做法: 先用 `v4l2_format_test /dev/video1 640 480 <fmt>` 测试驱动支持情况

## 10.4 10 道方案改进题

**Q51**: 如果要支持更高帧率 (如 30fps), 需要做哪些改进?
> **参考答案**:
> 1. 增加 REQBUFS count (3→6), 减少 DQBUF 等待 (v4l2_capture.c:166)
> 2. 考虑使用多线程: 采集线程 + 发送线程, 用队列解耦
> 3. 检查网络带宽: 640*480*2*30 ≈ 18.4 MB/s (RGB565), 接近 100Mbps 以太网上限
> 4. 使用 MJPEG 压缩降低带宽: `-f MJPEG`
> 5. 将 timestamp_us 改为更准确的 monotonic clock (CLOCK_MONOTONIC)
> 6. 在驱动侧设置 VIDIOC_S_PARM 降低曝光时间

**Q52**: 如果要支持多客户端同时接收 (广播), 架构如何调整?
> **参考答案**:
> 1. 发送端: 维护客户端 fd 列表, 每帧对所有客户端 send_all
> 2. 或改用 UDP 组播: socket(AF_INET, SOCK_DGRAM), setsockopt IP_MULTICAST
> 3. 注意: TCP 组播不现实, 需要用 UDP 或维护多个 TCP 连接
> 4. 数据可靠性: UDP 丢包需应用层重传; TCP 多播需在发送端串行发送或 fork 子进程
> 5. 当前代码改造成本: send_all 调用处改为 for 循环遍历客户端列表

**Q53**: 如何添加 JPEG 硬件编码支持来降低网络带宽?
> **参考答案**:
> 1. i.MX6ULL 没有硬件 JPEG 编码器 (仅 i.MX6Q/D 有 IPU)
> 2. 可以用 libjpeg-turbo 做软件编码 (ARM NEON 优化)
> 3. 或使用 OV5640 传感器自身的 JPEG 输出模式 (S_FMT V4L2_PIX_FMT_MJPEG)
> 4. 当前代码已支持 MJPEG 传输 (frame_proto.h 中有定义), 但 MJPEG 依赖传感器直出
> 5. 改动: 发送端增加 MJPEG 格式判断 (不转码), PC 端增加 JPEG→RGB 解码 (libjpeg)

**Q54**: 如何实现采集和发送的并行化 (流水线)?
> **参考答案**:
> 1. 需要增加线程: pthread_create 采集线程, 主线程做 TCP 发送
> 2. 共享队列: 环形 buffer (struct {void *data; size_t size; int idx;}), 需要 mutex + cond
> 3. 注意: mmap buffer 使用后不能立即 QBUF (数据在发送中), 需在发送完成后 QBUF
> 4. 当前 DQBUF→发送→QBUF 的串行模式需改为 DQBUF→放入队列→[线程唤醒]→发送→QBUF
> 5. V4L2 buffer 数量需增加 (如 6 个) 以避免饥饿

**Q55**: 如何处理网络断线重连?
> **参考答案**:
> 1. 发送端增加重连逻辑: send 失败后 close(sockfd), 循环 tcp_client_connect 重试
> 2. 需要设置重连间隔: sleep(1) 避免 CPU 空转
> 3. 需要处理 frame_id 连续性: 重连后 reset 或从断点继续
> 4. 接收端: accept 循环, 处理连接断开后重新 accept
> 5. 当前代码: send 失败直接 break 退出, 需要改为重连逻辑
> 参考: tcp_client_connect 函数可复用 ([tcp_socket.c:83-116](src/tcp_socket.c#L83-L116))

**Q56**: SDL2 显示当前使用 1:1 像素映射, 如何支持窗口缩放时的画面自适应?
> **参考答案**:
> 1. SDL_WINDOW_RESIZABLE 已设置 (pc_receiver.c:144), 但纹理大小固定为首帧尺寸
> 2. 需要在 SDL_WINDOWEVENT_RESIZED 事件中重新创建纹理或使用 SDL_RenderSetLogicalSize
> 3. 当前 SDL_RenderCopy 使用 NULL 源矩形和目标矩形, 默认全窗口拉伸
> 4. 如需保持宽高比: 计算 letterbox/pillarbox 目标矩形

**Q57**: 如何增加录制功能 (保存视频文件而非单帧)?
> **参考答案**:
> 1. 使用 libavcodec/libavformat (FFmpeg) 编码和封装
> 2. 或简单地保存连续帧序列 (当前已实现), 用 ffmpeg 命令行后合成
> 3. 增加循环缓冲区录制: 在内存中保存最近 N 帧, 收到信号后写入磁盘
> 4. 在 pc_receiver 中增加 -r 参数表示录制文件路径
> 5. 复杂度: 视频编码需要处理时间戳、关键帧、编码器初始化等

**Q58**: framebuffer 显示当前输入支持 YUYV 和 RGB565 (输出统一 XRGB8888), 如何增加对其他格式的支持?
> **参考答案**:
> 1. 在 fb_display_show_frame 的分支中增加新的格式判断, 新增对应的 fb_copy_* 转换函数 (输出统一走 fb_pack_rgb888 打包)
> 2. MJPEG: 需要软件解码 (libjpeg), 成本高不适合低端 ARM
> 3. UYVY/YVYU/VYUY: 增加对应的转换函数 (模式与 YUYV 类似, 仅字节提取方式不同)
> 4. 若换用 16bpp LCD: init 中的 bpp 检查与打包逻辑需要相应调整
> 5. 参考 pc_receiver.c 中已有的 8 种转换函数实现

**Q59**: 如何实现动态帧率控制 (根据网络状况自适应)?
> **参考答案**:
> 1. 发送端测量: 记录 send_all 耗时, 计算实际帧率
> 2. 如果 send 耗时 > 帧间隔, 跳帧: 采集后立即 QBUF 不发送
> 3. 需要修改 imx6ull_sender 循环 (行 251-309), 增加跳帧计数器和条件判断
> 4. 简单实现: 在发送前检查上一次发送是否完成, 未完成则 skip 当前帧
> 5. 更完善的实现: 维护 send buffer 积压量, 积压超过阈值时自动跳帧

**Q60**: 如果要移植到其他 ARM 平台 (如 STM32MP1/RK3399), 需要修改哪些部分?
> **参考答案**:
> 1. Makefile: 修改 CROSS_COMPILE 和 TOOLCHAIN_DIR
> 2. 如果目标平台也是标准 V4L2: v4l2_capture.c 几乎不需要修改
> 3. 如果使用不同接口 (如 ISP 而非 CSI): 可能需要修改 S_FMT 格式处理逻辑
> 4. 驱动 quirk: 需要针对新平台的驱动做类似的兼容性测试 (G_FMT/S_FMT 行为)
> 5. framebuffer: 如果使用 DRM/KMS 代替 fbdev, 需要重写 fb_display.c
> 6. 网络: tcp_socket.c 是标准 POSIX, 不需要修改
> 7. PC 端 (pc_receiver.c) 完全不需要修改

# 11. 一分钟项目介绍

## 11.1 30 秒版本

> 我在 i.MX6ULL 嵌入式平台上做了一个 V4L2 摄像头图像通过 TCP 实时传输到 PC 的项目。板端用 V4L2 MMAP 方式从 OV5640 摄像头采集图像帧, 通过自定义的 TCP 帧协议 (40 字节帧头 + 原始图像数据, 全部网络字节序) 发送到 PC。PC 端作为 Server 接收后保存 raw 文件, 同时转成 PPM 格式可以预览, 还支持 SDL2 窗口实时显示, 切换 8 种像素格式。整个采集流程是标准的 V4L2 流程: open → QUERYCAP → S_FMT → REQBUFS → mmap → STREAMON → poll/DQBUF 循环。

## 11.2 1 分钟版本

> 这个项目解决的是 i.MX6ULL 平台 OV5640 摄像头的实时图像采集和网络传输。核心是三个模块:
>
> 第一个是 V4L2 采集模块 (v4l2_capture.c, 528 行), 实现完整的 MMAP 流式 I/O 流程。这里遇到一个关键问题是 Linux 4.1.15 的 mx6s-csi (mx6s_capture) 驱动 G_FMT 会返回无效值, 所以我改成了以 S_FMT 返回值为准, 不用 G_FMT 覆盖。这个决策是整个项目能稳定运行的基础。
>
> 第二个是 TCP 帧协议, 我定义了一个 40 字节的帧头, 包含魔数、宽高、像素格式、帧序号和微秒时间戳, 全部用 htonl/ntohl 做网络字节序转换, 保证 ARM 板和 PC 之间字节序一致。传输层用 send_all/recv_all 保证完整传输。
>
> 第三个是 PC 端做的颜色转换管线, 支持 8 种像素格式: 4 种 RGB565 变体 (LE/BE, 正常/RB 交换) 和 4 种 YUV 4:2:2 变体 (YUYV/UYVY/YVYU/VYUY), 都转成 RGB888 然后 SDL2 显示。这里还加了键盘快捷键 1-8 实时切换解码格式, 方便调试 i.MX6ULL 的 CSI R/B 交换问题。
>
> 另外还做了 framebuffer LCD 本地显示和两个独立的诊断工具, 工具独立编译不依赖采集库, 方便现场排查摄像头问题。

## 11.3 3 分钟版本

> 我想详细介绍一下这个 i.MX6ULL OV5640 摄像头 TCP 图传项目, 从硬到软的全链路。
>
> **项目背景和硬件平台**:
> 平台是 NXP i.MX6ULL (Cortex-A7), 内核 4.1.15, 交叉工具链用的是 Linaro GCC 4.9.4。摄像头是 OV5640, 8-bit 并行 DVP 接口 (i.MX6ULL 没有 MIPI CSI), 通过 mx6s-csi (mx6s_capture) 驱动暴露为 V4L2 设备节点 /dev/video1。整个项目代码约 2000 行, 分板端和 PC 端两部分, 另外还修改了内核树中的两个驱动。
>
> **V4L2 采集是核心**:
> 我实现了完整的 V4L2 MMAP 采集流程: open → VIDIOC_QUERYCAP → VIDIOC_S_FMT → VIDIOC_REQBUFS(count=3) → VIDIOC_QUERYBUF×3 → mmap×3 → VIDIOC_QBUF×3 → VIDIOC_STREAMON → 循环 poll+DQBUF。每一步都有完整的错误处理和资源回滚 (goto fail_map 标签 munmap 已成功的 buffer)。
>
> 开发过程中发现一个关键问题: Linux 4.1.15 的 mx6s-csi (mx6s_capture) 驱动, VIDIOC_G_FMT 会返回 pixelformat=0 和 bytesperline=0, 是无效的。所以 S_FMT 之后不能用 G_FMT 覆盖, 必须以 S_FMT 返回值为准。为了解决这个问题, 我还写了一个独立的 v4l2_format_test 诊断工具, 做 ENUM_FMT→TRY_FMT→S_FMT→G_FMT 四步对比, 确认 S_FMT 最可靠。
>
> **TCP 帧协议设计**:
> 我设计了一个 40 字节的帧头, 包含 8 个 uint32_t 和一个 uint64_t: 魔数 0x12345678 做边界校验、协议版本、帧头大小、图像宽高、像素格式 FOURCC、数据长度、帧序号和采集时间戳。所有字段在发送端用 htonl 转网络字节序, 接收端用 ntohl 转回来。数据部分直接跟在帧头后面, 一帧完整的 TCP 报文 = 40 字节帧头 + size 字节图像数据。
>
> **颜色转换和显示是难点**:
> 像素格式这块比较复杂。标准 V4L2 有 RGB565 (LE) 和 RGB565X (BE), 但 i.MX6ULL 的 CSI 控制器在硬件层面做了 R/B 通道交换, 实际输出的数据用 BGR565 解码才有正确颜色。另外 YUV 4:2:2 有 4 种字节顺序: YUYV, UYVY, YVYU, VYUY, 分别对应不同的 Y/U/V 排列方式。我在 PC 端实现了全部 8 种格式到 RGB888 的转换函数, 支持 SDL2 窗口实时显示, 按键盘 1-8 就可以切换解码格式, 按 0 回到自动检测。标题栏会同时显示帧头里的格式和当前实际解码格式, 方便调试。
>
> **其他功能**:
> 板端还支持 framebuffer LCD 本地显示, 直接 mmap 显存写入。对 YUYV 格式做了 BT.601 定点转换到 XRGB8888 (避免浮点)。这里还踩过一个坑: 板载 LCD 是 32bpp XRGB8888, 一开始按 RGB565 16 位直接写显存导致画面泛绿、像素错位, 后来改为按 line_length/bytesperline 计算行步长、每像素写 uint32_t 后解决。整个项目做了完整的信号处理实现优雅退出 (Ctrl+C 后 STREAMOFF→munmap→close), Makefile 支持 ARM 交叉编译和 PC 本地编译双目标, NFS 一键安装到开发板。
>
> **我个人在这个项目中的收获**:
> 一是深入理解了 V4L2 框架的 MMAP 采集流程和不同驱动的兼容性问题; 二是掌握了图像像素格式在字节层面的处理 (RGB 位扩展、BT.601 转换、字节顺序); 三是学会了如何在遇到驱动限制时用应用层策略弥补, 比如 G_FMT 不可靠就改用 S_FMT, 颜色不确定就做多种解码格式让用户切换。
