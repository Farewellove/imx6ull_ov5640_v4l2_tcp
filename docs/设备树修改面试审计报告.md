# 2. 逐节点解析

## 2.1 CSI 控制器节点 (行 228-236)

```dts
&csi {
	status = "okay";

	port {
		csi1_ep: endpoint {
			remote-endpoint = <&ov5640_ep>;
		};
	};
};
```

- `status = "okay"`: 使能 CSI 控制器 (基节点在 imx6ull.dtsi, compatible `fsl,imx6s-csi`, 与 mx6s_capture.c 的 of_device_id 匹配)
- `port/endpoint` + `remote-endpoint`: **V4L2 异步子设备绑定**的标准写法 (of_graph)。驱动侧对应 `mx6sx_register_subdevs()` (mx6s_capture.c:1900-1945): 遍历 csi 节点的 port 子节点, 用 `of_graph_get_remote_port_parent()` 找到传感器节点, 注册 v4l2_async_notifier。当 ov5640 驱动 `v4l2_async_register_subdev()` 后, 两者完成绑定

## 2.2 OV5640 传感器节点 (行 357-379)

```dts
ov5640: ov5640@3c {
	compatible = "ovti,ov5640";
	reg = <0x3c>;
	pinctrl-names = "default";
	pinctrl-0 = <&pinctrl_csi1
					&csi_pwn_rst>;
	clocks = <&clks IMX6UL_CLK_CSI>;
	clock-names = "csi_mclk";
	pwn-gpios=<&gpio1 4 1>;
	rst-gpios = <&gpio1 2 0>;

	/*pwn-gpios = <&gpio_spi 6 1>;
	rst-gpios = <&gpio_spi 5 0>;*/
	csi_id = <0>;
	mclk = <24000000>;
	mclk_source = <0>;
	status = "okay";
	port {
		ov5640_ep: endpoint {
			remote-endpoint = <&csi1_ep>;
		};
	};
};
```

| 属性 | 值 | 含义 | 驱动侧对应 (ov5640.c) |
|------|-----|------|----------------------|
| `compatible` | "ovti,ov5640" | 设备兼容性字符串 | 驱动**无 of_match_table**, 靠 i2c_device_id 表 "ov5640" 匹配 (见 Q7) |
| `reg` | 0x3c | I2C1 总线上的 7-bit 地址 (0x3c, 写=0x78 读=0x79) | i2c_client->addr |
| `pinctrl-0` | 两个组 | pinctrl_csi1 (12 根 CSI 信号) + csi_pwn_rst (pwdn/rst GPIO) | probe 中 `devm_pinctrl_get_select_default()` 一次选上两个组 |
| `clocks` | IMX6UL_CLK_CSI | MCLK 时钟源 (CCM) | probe `devm_clk_get(dev, "csi_mclk")` 按 clock-names 匹配 |
| `clock-names` | "csi_mclk" | 时钟名 | 同上 |
| `pwn-gpios` | gpio1 4 1 | GPIO1_IO04, 第 3 个 cell=1 表示 GPIO_ACTIVE_HIGH 标志 | probe `of_get_named_gpio("pwn-gpios")` 申请为输出 (初始高 = 掉电) |
| `rst-gpios` | gpio1 2 0 | GPIO1_IO02, flags=0 | 同上, 复位脚 |
| `csi_id` | 0 | 绑定的 CSI 通道编号 | probe 读出存入 ov5640_data.csi, **并行版驱动中未再使用** (MIPI 版遗留属性) |
| `mclk` | 24000000 | MCLK 目标频率 24MHz | probe `ov5640_set_clk_rate()` → clk_set_rate(sensor_clk, 24MHz) |
| `mclk_source` | 0 | 时钟来自引脚 (CSI_MCLK pad) | probe 读出存入 mclk_source, 未参与逻辑 |
| `port/endpoint` | remote-endpoint | 与 &csi 互指 | 异步绑定 |

## 2.3 pwn/rst GPIO 组 (行 433-438)

```dts
//车载终端 OV5640电源引脚和reset引脚
csi_pwn_rst: csi_pwn_rstgrp {
	fsl,pins = <
		MX6UL_PAD_GPIO1_IO02__GPIO1_IO02	0x10b0 	/*reset引脚*/
		MX6UL_PAD_GPIO1_IO04__GPIO1_IO04	0x10b0	/*电源引脚*/
	>;
};
```

- 两根 GPIO: IO02=reset, IO04=pwdn (电源控制), pad 值 0x10b0
- 0x10b0 位域分解: HYS=1, PUS=00 (100K 下拉), PUE=1, PKE=1, SPEED=10 (100MHz), DSE=110, SRE=0
- 注意与 ov5640 驱动 probe 的申请顺序对应: pwdn 先申请 (初始高=掉电), rst 后申请 (初始高)

## 2.4 CSI 并行信号组 (行 442-455)

```dts
pinctrl_csi1: csi1grp {
	fsl,pins = <
		MX6UL_PAD_CSI_MCLK__CSI_MCLK		0x13088	/* 100K PD, LED off when MCLK disabled */  ← 本人修改
		MX6UL_PAD_CSI_PIXCLK__CSI_PIXCLK	0x1b088
		MX6UL_PAD_CSI_VSYNC__CSI_VSYNC		0x1b088
		MX6UL_PAD_CSI_HSYNC__CSI_HSYNC		0x1b088
		MX6UL_PAD_CSI_DATA00__CSI_DATA02	0x1b088
		MX6UL_PAD_CSI_DATA01__CSI_DATA03	0x1b088
		MX6UL_PAD_CSI_DATA02__CSI_DATA04	0x1b088
		MX6UL_PAD_CSI_DATA03__CSI_DATA05	0x1b088
		MX6UL_PAD_CSI_DATA04__CSI_DATA06	0x1b088
		MX6UL_PAD_CSI_DATA05__CSI_DATA07	0x1b088
		MX6UL_PAD_CSI_DATA06__CSI_DATA08	0x1b088
		MX6UL_PAD_CSI_DATA07__CSI_DATA09	0x1b088
	>;
};
```

**要点 1: 8-bit 并行 DVP 的完整信号组** — MCLK + PIXCLK + VSYNC + HSYNC + DATA[0:7] 共 12 根, 与 i.MX6ULL 并行 CSI 接口对应, 是 "OV5640 走 8-bit 并行总线" 的设备树级证据 (i.MX6ULL 无 MIPI CSI 控制器)。

**要点 2: 数据线映射的特殊性** — `MX6UL_PAD_CSI_DATA00__CSI_DATA02` 表示物理 pad CSI_DATA00 复用为 **CSI_DATA02 信号**。即正点原子板硬件把 OV5640 的 D0-D7 接到了 CSI 的 DATA02-DATA09 信号位上 (DATA00/DATA01 未接)。这是板级布线决定的, 属于背景知识, 非本人修改。

# 3. 本人修改点 (已确认)

## 3.1 CSI_MCLK pad: 0x1b088 → 0x13088 (2026-07-03, 闪光灯修复第一层)

```
-		MX6UL_PAD_CSI_MCLK__CSI_MCLK		0x1b088
+		MX6UL_PAD_CSI_MCLK__CSI_MCLK		0x13088	/* 100K PD, LED off when MCLK disabled */
```

pad control 完整位域分解 (i.MX6ULL IOMUXC SW_PAD_CTL):

| 位域 | 位 | 0x1b088 | 0x13088 | 含义 |
|------|-----|---------|---------|------|
| HYS | 16 | 1 | 1 | 输入迟滞使能 |
| **PUS** | **15:14** | **10** | **00** | **10=100K 上拉 → 00=100K 下拉 (本次唯一改动)** |
| PUE | 13 | 1 | 1 | 上拉/保持器使能 |
| PKE | 12 | 1 | 1 | 拉/保持功能使能 |
| ODE | 11 | 0 | 0 | 开漏输出关闭 |
| SPEED | 7:6 | 10 | 10 | 100MHz 速率档 |
| DSE | 5:3 | 001 | 001 | 驱动强度最低非零档 (000=输出关闭) |
| SRE | 0 | 0 | 0 | 慢压摆率 |

⚠️ **笔误提醒**: 之前的修复日志 (ov5640-flash-fix-changelog.md 和 interview-summary.md) 中把 DSE 写成 "110", 实际 0x1b088/0x13088 的 bits[5:3] = **001** (DSE=110 是 0x10b0/0x1b0b0 的值, 分解时混淆了)。面试若被追问现场算位会露馅, 建议以本表为准并对照 IMX6ULLRM IOMUXC 章节。

**为什么改**: 闪光灯 LED 物理连接在 CSI_MCLK 引脚 (高电平亮)。原配置 PUS=10 (100K 上拉), MCLK 关闭输出后引脚高阻, 被上拉电阻拉到高电平 → LED 常亮。改 PUS=00 (100K 下拉) 后, MCLK 关闭时引脚被拉低 → LED 灭。

**为什么只改 DTS 不够**: 这是三层根因的第一层。CCM 时钟关闭后 CSI 模块的 MCLK 输出级仍保持使能 (恒高), 100K 下拉压不住, 所以还有驱动层修复: (1) 删除 mx6s_csi_deinit 中重新打开 MCLKEN 的 csi_init_interface 调用; (2) ov5640.c 中不用 MCLK 时把引脚从 ALT0 (CSI_MCLK) 动态切到 ALT5 (GPIO4_IO17) 输出低。完整链条见主审计报告 7.8 节和 /home/why/Log/ov5640-flash-fix-changelog.md。

# 5. 面试 Q&A

**Q1**: `0x1b088` 这个 pad 值每个位域代表什么?
> **答案**: bit16 HYS=1 迟滞; bit15:14 PUS=10 → 100K 上拉; bit13 PUE=1 拉使能; bit12 PKE=1 保持器使能; bit7:6 SPEED=10 → 100MHz; bit5:3 DSE=001 驱动强度; bit0 SRE=0 慢压摆率。PUS 编码: 00=100K 下拉, 01=47K 上拉, 10=100K 上拉, 11=22K 上拉。

**Q2**: 为什么把 CSI_MCLK 的 pad 从 100K 上拉改成 100K 下拉?
> **答案**: 本板闪光灯 LED 物理连接在 CSI_MCLK 引脚 (高电平亮)。MCLK 不输出时引脚高阻, 100K 上拉会把电平拉高 → LED 常亮; 改 100K 下拉后空闲时被拉低 → LED 灭。

**Q3**: 只改 pad 下拉为什么解决不了问题?
> **答案**: 因为 CCM 时钟关闭后 CSI 模块 MCLK 输出级仍处于使能状态, 引脚被驱动为恒高, 弱下拉 (100K) 压不住。所以还有两层修复: 驱动 deinit 不再重新打开 MCLKEN; 不用 MCLK 时用 IOMUXC 把引脚切到 GPIO 输出低。这是典型的"问题多层叠加"案例。

**Q4**: `pinctrl-0 = <&pinctrl_csi1 &csi_pwn_rst>;` 为什么有两个组?
> **答案**: 一个设备可以引用多个 pinctrl 组, 内核 pinctrl 子系统的 map 会把两组都应用。这里 pinctrl_csi1 管 12 根 CSI 信号线, csi_pwn_rst 管 pwdn/rst 两根 GPIO, 职责分开便于维护。

**Q5**: `pwn-gpios = <&gpio1 4 1>;` 三个 cell 分别是什么?
> **答案**: 第一个是 GPIO 控制器 phandle (gpio1), 第二个是控制器内的编号 (4 → GPIO1_IO04), 第三个是 GPIO 标志 (1 = GPIO_ACTIVE_HIGH)。驱动用 of_get_named_gpio 解析, devm_gpio_request_one 申请。

**Q6**: `&csi` 里的 port/endpoint/remote-endpoint 是干什么的?
> **答案**: 这是 V4L2/媒体子系统的 of_graph 拓扑描述: 用 endpoint 双向互指把 CSI 主机和 OV5640 传感器连接起来。CSI 驱动 probe 时遍历 port 子节点, 用 of_graph_get_remote_port_parent 找到对端节点, 注册 v4l2_async_notifier; 传感器驱动 v4l2_async_register_subdev 后完成绑定。有了这个绑定, CSI 的 ioctl 才能转发到 sensor 的 subdev 回调 (s_fmt/s_stream 等)。

**Q7**: compatible 是 "ovti,ov5640", 但 ov5640.c 里没有 of_match_table, 是怎么匹配上的?
> **答案**: 这是老内核 (4.1.15) 的机制。of_i2c 注册设备时 of_modalias_node 会把 compatible 的 vendor 前缀剥掉, client->name 变成 "ov5640", 然后 i2c_match_id 用 driver->id_table 中的 "ov5640" 严格 strcmp 匹配成功。较新内核要求 of_match_table, 老 freescale 驱动则依赖这个 fallback。

**Q8**: `clocks/clock-names` 是怎么和驱动代码对应的?
> **答案**: clock-names = "csi_mclk" 给时钟起名, 驱动用 devm_clk_get(dev, "csi_mclk") 按名字拿 clk; clocks 里 IMX6UL_CLK_CSI 是 CCM 中的时钟 ID (定义在 imx6ul-clock.h)。probe 里 ov5640_set_clk_rate() 再 clk_set_rate 到 DTS 的 mclk 值 24MHz。

**Q9**: 为什么数据线写的是 `MX6UL_PAD_CSI_DATA00__CSI_DATA02`?
> **答案**: 宏名格式是 "物理pad名__复用信号名"。本板原理图把 OV5640 的 D0-D7 接到了 CSI 控制器的 DATA02-DATA09 信号位, 所以 pad CSI_DATA00 被复用为 CSI_DATA02 信号。DTS 必须按实际板级布线写, 照抄官方 EVK 会不通。

**Q10**: `csi_id` 和 `mclk_source` 在并行版驱动里有什么用?
> **答案**: probe 只读出保存 (ov5640_data.csi / mclk_source), 不参与后续逻辑 —— 它们是 MIPI 版驱动的遗留属性 (MIPI 版需要 csi_id 选通道、mclk_source 选时钟来源)。保留是为了兼容同一份驱动多平台使用。能从代码里看出"属性读了但没用到", 是读驱动源码能力的体现。
