## 1. 现在就能写的内容（全部有原始数据或代码支撑）

### 1.1 推荐主句式（可直接放进简历）

> 基于 i.MX6ULL / Linux 4.1.15 实现 OV5640 V4L2 MMAP 图像采集、LCD 本地显示与自定义 TCP 帧协议图传；针对协议正确性补齐帧头多级校验与畸形帧分类拒绝，并通过可控分块测试验证接收端在 137B / 8KB / **1B** 三种分片粒度下均可逐字节完整重组（单次用例最大 12,288,000 B payload、接收端 82,332 次 `recv()` 调用、0 错误），同时修正了 64 位时间戳在网络字节序下随主机端序变化的一致性缺陷。

**证据**（工具已移出，指向代码与结论）:
- 畸形帧拒绝: `src/pc_receiver.c` 的 `rx_validate_header()` + `RX_MAX_FRAME_BYTES`
- 分片重组: `src/tcp_socket.c` 的 `recv_all_stat` 循环补齐
- 字节序: `include/frame_proto.h` 的 `frame_header_hton/ntoh`
- 详细结论与数字: `AUDIT_AND_CHANGES.md` §B2.1 / §2.2

### 1.2 第二条（工程健壮性，很戳面试官）

> 为采集/图传链路增加可复现的性能与资源统计能力（帧间隔分位数、`sequence` 跳变、短收发分片、进程 CPU/RSS、板内阶段耗时，输出 CSV 与汇总），并把统计与校验全部做成默认关闭的可选开关，保持原有默认行为不变；同时定位并消除三处无限阻塞风险（`accept()`、`send()`/`recv()` 无超时、脚本无界等待），将端到端测试改造成带三层超时护栏的自动化套件。

**证据**: `src/metrics.c`、`src/imx6ull_sender.c`（`--stats-dir` 等）、
`src/pc_receiver.c`（`--accept-timeout`/`--io-timeout`）、`performance_evaluation/scripts/board_benchmark.sh`（板端用例超时护栏）

### 1.3 第三条（协议与字节序, 适合被追问细节）

> 通过自建帧协议单元测试发现 64 位时间戳字段的序列化在大小端主机上产生不同线格式（`htonl` 整数拼接的典型陷阱），改为逐字节写出高/低 32 位并统一收发两端与测试工具共用同一份实现，协议版本升至 2 并由校验层显式拒绝版本不匹配的帧，避免静默产生错误时间戳。

**证据**（工具已移出，证据保留为实测字节转储）:
`include/frame_proto.h` 中 `frame_header_hton()` 现为**逐字节**写
`ts[0..3]=BE(hi)`、`ts[4..7]=BE(lo)`；旧/新写法的实测字节对比为
`legacy v1: FF FF FF FF 00 00 00 01` vs `fixed v2: 00 00 00 01 FF FF FF FF`。

### 1.3b 双指手势缩放（2026-10-13 新增能力）

> 整合 GT911 电容触摸，基于 Linux input 子系统的 **MT Protocol B** 实现双指手势驱动的
> 视频数字缩放（1.0×–2.0×）：以双指距离比例做缩放、以双指中心为缩放中心并支持平移；
> 缩放仅作用于 framebuffer 显示阶段。渲染采用最近邻插值 + **行解码缓存**（放大时复用
> 源行，减少约 37% 的解码量），并通过合成 framebuffer 的 **guard 区 + 每行行尾填充区
> 双重越界检查**与 2200 帧连续缩放扫描验证无越界、几何逐位匹配 12,642 个采样点。

**证据**（离线测试工具与日志已于 2026-10-13 移出项目，结论保留、证据指向代码）:
`src/gesture_zoom.c`（手势判定与 `fb_view_clamp` 边界钳制）、
`src/fb_display.c:fb_display_show_frame_zoomed`（行缓存 + 越界哨兵）、
`performance_evaluation/PERFORMANCE.md` §3（历史结论）

> ⚠️ 上面**没有**给出任何板端耗时数字 —— 离线测的是宿主机。板端 1.0/1.5/2.0× 的
> `render_mean/p95/p99/max` 需按 `USAGE.md` §12.3 在板上跑 `board_zoom_bench.sh` 后补。

## 3. 关于 `mx6s_csi G_FMT` 问题的正确说法（面试高频）

**问题**: 面试官如果问"你遇到过什么驱动相关的坑", 这个点很好用, 但**口径极易说错**。

| 说法 | 是否可用 | 说明 |
|---|---|---|
| "G_FMT 会返回 pixelformat=0, 所以我改成以 S_FMT 为准" | ✅ 可用 | 这是应用层策略, 代码在 `src/v4l2_capture.c:92-160` 且有注释 |
| "根因是原厂驱动的 probe 从不初始化 `csi_dev->pix`, 而 `g_fmt` 只是把它原样拷回（`mx6s_capture.c:1612`）, 所以 S_FMT 之前调 G_FMT 会拿到全零" | ✅ 可用 | 定位过程与驱动源码证据完整 |
| "我还写了个 `v4l2_format_test` 做 ENUM_FMT→TRY_FMT→S_FMT→G_FMT 四步对比来定位" | ✅ 可用（**工具本身已于 2026-10-13 作为清理移出项目**，但这段排查经历是真实的；被追问细节就讲方法与根因，不要说"代码还在仓库里"） | 结论在 `AUDIT_AND_CHANGES.md` §A5.4 |
| "我在驱动 probe 里初始化了默认格式, 修复并验证了 G_FMT" | ⚠️ **需谨慎** | 该修复**已存在于本内核树**（`mx6s_capture.c:2007-2013`）。若确为本人完成, 可以说"我在驱动 probe 中补充了默认格式初始化"; 否则应说"内核树中已有该修复"。**不要声称本轮修复**。 |
| "驱动是我从零写的" | ❌ 不可用 | 实际是在厂商/内核已有驱动上做适配与缺陷修复 |

**推荐完整回答**（约 40 秒）:

> "项目里遇到一个格式协商的坑: Linux 4.1.15 的 mx6s-csi 驱动, `VIDIOC_G_FMT` 会返回 `pixelformat=0`、`bytesperline=0`。我一开始以为是自己写的时序问题, 就写了个独立的 `v4l2_format_test` 工具做 ENUM_FMT→TRY_FMT→S_FMT→G_FMT 四步对比, 发现 S_FMT 返回值是对的, 只有 G_FMT 拿到了零值。后来读驱动源码定位到根因: `mx6s_vidioc_g_fmt_vid_cap()` 只是把内部结构 `csi_dev->pix` 原样拷回, 而驱动的 probe 从来没初始化过它, 只有 S_FMT 才会填充。所以这是驱动缺陷, 不是偶发时序问题。我的处理是应用层不再用 G_FMT 覆盖 S_FMT 结果, 把 S_FMT 作为唯一权威格式来源, G_FMT 失败只告警不致命; 内核树里也已经补上了 probe 的默认格式初始化。"

## 5. 面试可能被追问的技术点（附本项目里的确切答案位置）

| 追问 | 答案要点 | 代码位置 |
|---|---|---|
| 为什么用 MMAP 而不是 read/write？ | 避免每帧一次内核→用户拷贝; buffer 由驱动直接 DMA 写入, 用户态只映射指针 | `src/v4l2_capture.c:194-219` |
| `bytesused` 和 `length` 的区别？ | `length` 是 buffer 总容量（QUERYBUF 得到）, `bytesused` 是本帧有效字节数（DQBUF 得到）; 必须校验 `bytesused ≤ length` | `src/v4l2_capture.c:200` vs `:318-325` |
| QBUF 之后还能不能读那块内存？ | **不能依赖**。QBUF 归还后内核可重新拿去 DMA。本项目在 `QBUF` **之前**完成 `send_all`, 所以不存在这个竞态 | `src/imx6ull_sender.c` 主循环 |
| TCP 为什么会"粘包"？你们怎么处理？ | TCP 是字节流无消息边界; 用 40 字节定长帧头 + `size` 字段定长读取, 收发都用循环补齐 | `src/tcp_socket.c:26/81` |
| 怎么证明接收端真的处理了分片？ | 用一次性发送器强制按 1 字节/137 字节/8KB 分块发送, 接收端 `data_recv_calls` 远大于帧数（实测: 5 帧 40,960 B 用了 37,381 次 `recv()`）。**该发送器已移出项目**，但重组逻辑本身在 `recv_all_stat` 里 | `src/tcp_socket.c:81` |
| 为什么分位数用最近秩法而不是插值？ | 要回答的是"最差 1% 的帧耗多久", 取真实存在的样本比插值更有意义 | `src/metrics.c:103` |
| `/proc/<pid>/stat` 解析有什么坑？ | 第 2 字段 `(comm)` 可含空格与右括号, 必须从**最后一个 `)`** 之后解析 | `src/metrics.c:182` |
| 为什么 CPU 占用要两次采样做差？ | `/proc` 给的是累计 CPU 时间, 单次快照无法得到"占用率" | `src/metrics.c:258` |
| 怎么保证测试不会挂死？ | 三层: 程序内 `pc_receiver --accept-timeout` / 两端 `--io-timeout`；脚本里每个用例用 `timeout --kill-after` 包住；板端用例都带 `--duration`。**上板可直接复现**: `pc_receiver -p 5000 --no-save --accept-timeout 3` 什么都不做，3 秒后应自退 | `src/pc_receiver.c`（accept 前 `poll`）/ `scripts/board_benchmark.sh` |
| 项目最大的不足是什么？ | 协议无 CRC 与 `bytesperline` 字段; 采集与发送串行导致 3 缓冲只能吸收约 2 帧抖动; 板端 RGB565 直显未做 R/B 交换 —— 都在 `AUDIT_AND_CHANGES.md` §A6 列了 | `AUDIT_AND_CHANGES.md` |

## 6. 一句话版本（电梯陈述）

> 这是一个 i.MX6ULL + OV5640 的嵌入式图传项目: 用 V4L2 MMAP 采集、framebuffer 本地显示、自定义 TCP 帧协议传到 PC 端保存并用 SDL2 显示。我做的主要是两件事 —— 一是把协议和缓冲区的正确性补实（帧头多级校验、长度越界保护、用可控分块测试证明接收端在逐字节分片下也能完整重组, 还顺手修掉一个 64 位时间戳字节序不一致的缺陷）; 二是给整条链路加上可复现的量化能力（帧间隔分位数、`sequence` 跳变、短收发分片、CPU/RSS、板内阶段耗时, 全部输出 CSV）, 并且全部做成默认关闭的开关, 不影响原有功能。板端性能数据在无硬件环境下没有编造, 全部标记为待实测。
